# Bitproto C-To-Go TCP/IP Guide

This guide explains the practical design points for using bitproto between:
- C endpoints (including RTOS/Zephyr style code)
- Go TCP/IP servers

It focuses on payload length correctness, framing safety, and long-term operational stability.

## 1. Why This Matters

TCP is a byte stream, not a message queue.
You do not get packet boundaries from TCP reads.

For bitproto, this means:
- encode output bytes must be framed explicitly
- receiver must read exact frame boundaries before decoding

The recent API change to C generated code helps here:
- EncodeX returns payload length as size_t
- DecodeX returns consumed payload length as size_t

This provides an explicit and compiler-generated truth for payload sizing.

## 2. Recommended Frame Format

Use a compact fixed header before the bitproto payload, and define this header
with bitproto so C and Go share one schema.

Suggested header layout (4 bytes total):
- 0: magic (uint8, example constant 0xB1)
- 1: payload_type (enum uint8)
- 2..3: payload_length (uint16, big-endian on wire)

Example bitproto definition file for the frame header:

```bitproto
proto frame_meta;

enum PayloadType : uint8 {
	UNKNOWN = 0;
	REQUEST = 1;
	RESPONSE = 2;
	EVENT = 3;
}

message FrameHeader {
	uint8 magic = 1;
	PayloadType payload_type = 2;
	uint16 payload_length = 3;
}
```

Then append payload bytes from bitproto encode.

Notes:
- Keep one fixed magic constant for fast fail-fast validation.
- Validate payload_type against supported enum values.
- If payload can exceed 65535, switch payload_length to uint32.
- Keep network byte order for all multi-byte length fields.

## 4. C Side (RTOS/Zephyr) Critical Path

### Encode/send path

1. Fill message struct fields.
2. Call EncodeX(msg, payload_buf).
3. Use returned size_t payload_len as authoritative length.
4. Build frame header with payload_len.
5. Send header first, then payload.
6. Ensure send loop handles partial writes.

### Receive/decode path

1. Read fixed-size header with a loop until full.
2. Validate magic and payload_type.
3. Parse payload_len and validate upper bound.
4. Read payload_len bytes with a loop until full.
5. Call DecodeX(msg, payload_buf).
6. Validate returned decode length matches expected payload_len.

### Safety checks to keep

- hard cap payload_len against local buffer size
- timeout for header and payload reads
- close connection on malformed frame
- never decode before full payload is buffered

## 5. Go Server Critical Path

In the Go server implementation:
- use io.ReadFull for header and payload
- validate magic/payload_type/payload_length before decode
- compare length to generated BYTES_LENGTH_*
- decode only after full payload is read
- re-encode and reply using same framing

Reference implementation:
- [tests/test_encoding/encoding-cases/tcpip/go/main.go](tests/test_encoding/encoding-cases/tcpip/go/main.go)

## 6. Common Pitfalls To Avoid

1. Assuming one recv equals one message.
- Wrong for TCP stream semantics.

2. Ignoring partial send/recv.
- Must loop until expected bytes are processed.

3. Trusting peer length blindly.
- Validate before allocation and before read.

4. Decoding into struct before full frame arrival.
- Leads to undefined message content and silent corruption.

5. Mixing host endian and network endian in header length.
- Always encode header length in network byte order.

6. Reusing stale buffers without clearing policy.
- Keep deterministic initialization for safety-critical logic.

7. Letting malformed input continue on same connection.
- Prefer fail-fast and reconnect behavior.

8. Coupling transport framing with bitproto internals.
- Keep framing layer independent and simple.

## 7. Zephyr Integration Checklist

For future Zephyr deployment:

1. Transport abstraction
- Wrap socket/UART transport with read_exact and write_exact helpers.

2. Bounded memory
- Pre-allocate fixed header and payload buffers.
- Enforce compile-time max payload.

3. Timeouts and watchdog
- Apply per-stage timeout (header, payload, response).
- Reset connection on timeout.

4. Tasking model
- Keep parser/decoder in one dedicated context or protect state.
- Avoid data races on shared message structs.

5. Telemetry
- Count and report malformed headers, length violations, decode failures.

6. Versioning
- Evolve compatibility via payload_type values and protocol-level rules.
